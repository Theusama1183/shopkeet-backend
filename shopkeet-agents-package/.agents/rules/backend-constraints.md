# Rule: Backend architecture constraints

Applies to: all code under `apps/api/`. Load this rule for any backend task.

- MUST implement the backend as a single Go service. Do not create a second deployable service, even to isolate one new feature.
- MUST use Fiber as the only HTTP framework. Do not add a second framework, and do not replace it without an explicit instruction to do so.
- MUST use PostgreSQL as the only relational datastore. Do not introduce another SQL or NoSQL database.
- MUST treat Redis as a cache/queue layer only. Any data Redis holds must be reconstructable from Postgres. Never make Redis the only copy of a fact that matters — final inventory count and order status always resolve from Postgres.
- MUST NOT introduce Kafka, gRPC, an API gateway (KrakenD/Envoy/etc.), Kubernetes, a service mesh, or GraphQL for the internal API.
- MUST add a `tenant_id` column and a Row-Level Security policy to every new tenant-scoped table, in the same migration that creates the table. A table without RLS is not considered complete, even if it "obviously" only matters for one tenant right now.
- MUST NOT integrate a payment gateway — Stripe, PayPal, JazzCash, or any other. Payment method for v1 is Cash on Delivery only, via the `PaymentProvider` interface already defined in `internal/payments`. Adding a second provider requires an explicit instruction, not an assumption that it's helpful.
- MUST use Cloudflare R2 for all object storage (product/media images), accessed only through presigned URLs generated by `internal/media`. File bytes are never proxied through the Go API. R2 is a flagged, deliberate exception to "open source only" (see `docs/02-tech-stack.md`) — do not add a second storage provider without an explicit instruction, and do not treat the exception as license to add further proprietary infrastructure elsewhere.
- MUST use Puck (`@puckeditor/core`) for the page builder editor in `apps/web`. Do not build a custom drag-and-drop canvas.
- MUST set `app.current_tenant` via `SET LOCAL` inside the request's transaction on every authenticated request — this is what makes RLS actually apply. A handler that queries the database outside this pattern is a bug, not a style choice.
- MUST NOT deviate from this file without flagging the conflict first. If a task appears to require it, stop and raise the conflict rather than proceeding around it.

## Deployment constraint (supersedes the earlier "no Coolify" call — re-decided 2026-09-25)

- The API deploys via **Coolify** (app uuid `l6modsyezs1vlrv6ly1oqz4i`, source `Theusama1183/shopkeet-backend` `main`), NOT compose/Caddy. Caddy was dropped. This reverses the original compose+Caddy-for-RAM decision documented in `03-architecture.md`; Coolify was chosen because the frontend will deploy on it too, avoiding Vercel. `03-architecture.md` was updated to match.
- Current deployment is **hybrid**: only the Coolify app is Coolify-managed; `shopkeet-postgres` and `shopkeet-redis` are still the original manual containers attached to Coolify's Docker network. The app connects to them via hostname `shopkeet-postgres` / `shopkeet-redis` (never `postgres` — `coolify-db` owns that alias on the network).
- Mailpit (Coolify service) is the email sink in dev/staging. Real customer-facing email must go through a real relaying provider — set `RESEND_API_KEY` + `NOTIFICATIONS_FROM_EMAIL` (Resend free tier, 3000/mo) or point `SMTP_HOST*` at a relaying server. Do not ship to merchants with Mailpit as the only sink.

Full reasoning for these constraints: `docs/02-tech-stack.md`, `docs/03-architecture.md`, `docs/04-agent-build-spec.md §0`.
