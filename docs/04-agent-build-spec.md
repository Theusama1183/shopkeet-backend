# Shopkeet — Build Specification (for the implementing agent)

This is the working spec for building Shopkeet end to end. It assumes the reader is an AI coding agent (or a developer working alongside one) starting from an empty repo. Read `01-mission.md`, `02-tech-stack.md`, and `03-architecture.md` first for the "why" — this document is the "what, in what order, and how you'll know it's done."

**Build in the phases below, in order. Do not start a phase until the previous phase's acceptance criteria pass.** Each phase should be its own set of commits/PRs, small enough to review.

---

## Forward compatibility: public API & webhooks (not built now, designed for)

A third-party developer marketplace is explicitly **out of scope for v1** (see `01-mission.md`) — don't build one now. But developers will eventually need webhooks and a public API to build apps on Shopkeet, so build these seams in from day one so future work is additive, not a rewrite:

- **Emit internal domain events** wherever something meaningful happens (`order.created`, `order.paid`, `product.updated`, `inventory.low`). Use a small in-process pub/sub inside the Go monolith (`internal/platform/events`) rather than hardcoding side effects directly into business logic.
- Keep the internal REST API cleanly resourceful and versioned (`/api/v1/...`).
- Use JWT bearer auth rather than cookie-only auth for anything that could plausibly be called by an external app later.
- Don't return HTML or assume the only caller is your own Next.js app.

---

## 0. Non-negotiable constraints

These are architecture decisions already made — do not revisit them mid-build:

- **One Go backend service**, internally modular (`tenants`, `media`, `catalog`, `cart`, `orders`, `payments`, `content`). Do NOT split into separate microservices.
- **One Go web framework** for the whole service (Fiber). Do not introduce a second.
- **PostgreSQL only** as the primary datastore. No CockroachDB, no additional SQL databases.
- **Redis** is a cache/queue layer only — Postgres is always the source of truth. Nothing may treat Redis as authoritative.
- **No Kafka, no gRPC, no API gateway, no Kubernetes, no service mesh, no GraphQL** for the internal API.
- **Every tenant-scoped table has a `tenant_id` column and a Row-Level Security policy from the moment it's created.**
- **Payments: Cash on Delivery is the default and only method required for v1.** No payment gateway integration.
- **Object storage: Cloudflare R2 only**, accessed via presigned URLs generated by the `media` module. The Go API never proxies file bytes through itself. R2 is **not open source** — a deliberate, flagged exception to the open-source-only principle in `02-tech-stack.md`, alongside Cloudflare itself (DNS/edge). Do not add a second storage provider or route around this without an explicit instruction.
- **Page builder: use Puck (`@puckeditor/core`, MIT licensed)** in the frontend, not a hand-built drag-and-drop canvas. See Phase 6.

If a task seems to require breaking one of these, stop and flag it rather than proceeding.

## Phase 0 — Scaffolding

**Build:**
- `docker-compose.yml` with `postgres`, `redis`, `api`, `web` services.
- Go API skeleton: Fiber app, `GET /healthz` returning `200 {"status":"ok"}`, config loaded from env.
- Next.js skeleton: default app-router project, one placeholder home page.
- `golang-migrate` wired up with an empty initial migration.
- GitHub Actions workflow: build both apps, run `go vet` / `go test`, run `next build`.

**Acceptance:** `docker compose up` brings up all four services with no errors; `/healthz` returns 200; Next.js placeholder loads; CI passes.

## Phase 1 — Tenants & Auth

Apply `tenants`, `merchant_users` from `docs/schema.sql`.

- `POST /api/v1/auth/signup` — creates a tenant + owner user in one transaction, validates the subdomain.
- `POST /api/v1/auth/login` — issues a JWT (`tenant_id`, `user_id`, `role`).
- Auth middleware: validates JWT, runs `SET LOCAL app.current_tenant` inside the request's transaction so RLS applies automatically.
- Next.js `middleware.ts`: resolves tenant from subdomain/custom domain (see `03-architecture.md` §2).

**Acceptance:** a new merchant can sign up and log in; a test creates two tenants and asserts cross-tenant reads return nothing.

---

## Phase 2 — Media Library (Cloudflare R2)

Apply `media_assets` from `docs/schema.sql`. Endpoints per `docs/api-reference.md` §Media.

**Upload flow:**
1. Client calls `POST /media/upload-url` with a filename/content-type.
2. API generates a presigned R2 PUT URL scoped to a tenant-prefixed key (`{tenant_id}/{uuid}.{ext}`) and returns it — this is the only place R2 credentials are used.
3. Browser uploads the file bytes **directly to R2**, not through the Go API.
4. Client calls `POST /media` with the resulting key and metadata; the API records a `media_assets` row and returns the public URL.

**Acceptance:** a file uploaded through this flow is retrievable at its public URL; the Go API's request logs show no large file bodies passing through it; a cross-tenant request cannot list or delete another tenant's assets.

---

## Phase 3 — Catalog

Apply `categories`, `products`, `product_categories`, `product_images` from `docs/schema.sql`. Endpoints per `docs/api-reference.md` §Catalog.

- Product images attach existing `media_assets` (from Phase 2) via `product_images`, with a `sort_order` for gallery position.
- Postgres `tsvector` full-text search on `name`/`description` — no external search service yet.

**Acceptance:** Merchant A creates a product with two images; Merchant B's storefront and admin API cannot see or edit it; only `status = active` products are publicly listed; product images return in gallery order.

---

## Phase 4 — Cart & Inventory

Apply `carts`, `cart_items` from `docs/schema.sql`. Endpoints per `docs/api-reference.md` §Cart.

- Redis: `SETNX shopkeet:reserve:{product_id}:{unit_index}` with a 15-minute TTL on add-to-cart.
- Checkout-time confirmation: `SELECT inventory_count FROM products WHERE id = $1 FOR UPDATE` inside a transaction — the real guard against overselling; Redis just makes the common case fast.

**Acceptance:** two concurrent add-to-cart requests for the last unit of stock — exactly one succeeds at checkout, not at add-to-cart time.

---

## Phase 5 — Checkout & Orders (Cash on Delivery)

Apply `orders`, `order_items` from `docs/schema.sql`. Endpoints per `docs/api-reference.md` §Checkout & Orders.

- `payments` module implements the `PaymentProvider` interface with one provider: `cod`. No external gateway calls.
- `POST /checkout` validates stock (Phase 4's `FOR UPDATE` transaction), creates the order (`payment_method='cod'`, `payment_status='pending'`), decrements inventory, clears the cart, emits `order.created`.
- `PATCH /orders/:id/status` moves `pending → confirmed → shipped → delivered`; reaching `delivered` sets `payment_status='paid'` and emits `order.paid`.

**Acceptance:** a guest completes COD checkout, the order appears in admin as `pending`/`pending`, inventory decrements exactly once, and the merchant can move it to `delivered` + `paid`.

---

## Phase 6 — Content & Page Builder

Apply `posts`, `templates`, `sections`, `redirects` from `docs/schema.sql`. Endpoints per `docs/api-reference.md` §Content & Page Builder.

Three distinct concepts — don't collapse them into one:

- **Posts** (`post_type`: `page`, `blog_post`, ...) — one-off content a merchant writes by hand. Required for v1: `page` (home, about, etc.). `blog_post` is schema-ready but not required to ship.
- **Templates** (`template_type`: `product`, `product_archive`, `cart`, `404`, `order_confirmation`, ...) — one layout per type per tenant (`scope='default'`), applied across every matching instance (every product renders through the *one* `product` template). Required for v1: `product`, `product_archive`, `cart`, `404`, `order_confirmation`. `blog_archive` and `search_results` are schema-ready, not required to ship.
- **Sections** (`section_type`: `header`, `footer`, `announcement_bar`, `popup`) — global chrome, not tied to a route. Required for v1: `header`, `footer`. `announcement_bar` and `popup` (with `placement_rules` for trigger/pages/frequency) are schema-ready, not required to ship.

**Checkout is deliberately excluded from the template system** — it is not builder-editable. Letting merchants freely re-block checkout risks breaking conversion, legal correctness, and PCI hygiene; it gets color/logo theming only, wired directly in `web`, not a `templates` row.

**Page builder implementation:** use **Puck** (`@puckeditor/core`) in `apps/web`'s admin — do not build a custom drag-and-drop canvas. Define Shopkeet's blocks (`HeroBanner`, `ProductGrid`, and others as needed) as Puck's `config.components`; Puck's editor UI (canvas, drag/drop, undo/redo, prop panels) comes from the library. `onPublish` saves Puck's JSON output directly into the relevant `layout` column (`posts.layout`, `templates.layout`, or `sections.layout`) — no transformation needed, the schema was designed to match Puck's data model directly.

**Redirects:** when a merchant changes a post's `route`, create a `redirects` row from the old path. Next.js middleware checks `GET /redirects/lookup?path=...` before falling through to the `404` template.

**SEO:** `posts`/`products` have `meta_title`/`meta_description`; `posts` also has `og_image_id` referencing `media_assets`. Populate these in the relevant editors, even minimally, from the start — retrofitting SEO fields after merchants have live content is disruptive.

**Acceptance:** a merchant edits the `page` post at `route='/'` and the storefront reflects it without a deploy; every product renders through the single `product` template; changing a post's route creates a working redirect from the old path; a request to a nonexistent route renders the `404` template, not a framework default error page.

**Deferred, not required for v1** (see `docs/api-reference.md`'s "not built yet"): `blog_archive`/`search_results` templates, `announcement_bar`/`popup` sections, post/template revision history, a coming-soon/password-protected site mode.

## Phase 7 — Observability & hardening

**Build:**
- `/metrics` (Prometheus format): request count/latency/error rate by route, DB pool stats.
- Structured JSON logging: request id, tenant id, latency.
- Grafana dashboard checked into `infra/`.
- Consistent JSON error shape on every handler; recover middleware so no panic reaches the client.

**Acceptance:** dashboards render real data from a local run; a deliberately malformed request returns the standard error shape and shows up in logs/metrics, not a raw 500 stack trace.

## Conventions

- **Go:** standard project layout; table-driven tests per package; `tenant_id`/`context.Context` threaded through every DB call, never a global; wrap errors with context.
- **Migrations:** one file per change, sequential, never edit an already-applied migration.
- **Next.js:** App Router, server components by default, a single typed API client module (`lib/api.ts`).
- **Tests:** every phase's acceptance criteria exists as an automated test.
- **Commits:** one phase's work reviewable as a small number of focused PRs, not one giant commit.

## Definition of done for v1

All eight phases' acceptance criteria pass, end to end, on a fresh `docker compose up`: a new merchant signs up, gets a subdomain, uploads product photos to R2, adds a product, customizes their homepage and product page via Puck, and a test customer completes a real Cash-on-Delivery purchase — with Grafana showing the traffic as it happens.
